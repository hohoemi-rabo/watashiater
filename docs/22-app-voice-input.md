## 検証結果（2026-08-14・実機でユーザー確認）

- 環境：Xiaomi（HyperOS）／ Android 16（BP2A.250605.03）／ Expo Go（SDK 54）／
  入力は Gboard の音声入力。検証は一時画面 `voice-check.tsx`（録音＋TextInput を同居させ、
  metering 生値と statusListener を可視化。検証後に削除済み）
- **ベースライン**：録音していない状態では、TextInput へのキーボード音声入力は問題なく動く
- **同時動作は不可**：expo-audio が録音中（マイク保持中）にキーボードのマイクを押すと、
  Gboard が**「音声を受信できません。しばらくしてからもう一度お試しください。」**を出して
  音声入力が失敗する（文字は1文字も入らない）
- **録音側は無傷**：音声入力の失敗中も metering は動き続け（-31.9 など実値）、hasError なし、
  停止後の再生も途切れ・無音区間なし。**マイクの排他は「録音が勝つ」方向**で安定していた
- 前提の再確認：Expo Go にはプログラム用の音声認識モジュール（`@react-native-voice/voice` 等）を
  入れられない（dev build が必要）。「端末標準の音声認識」の実体はキーボードのマイクであり、
  検証すべきは上記のマイク排他だけだった

## 採用したUX（判断）

- **録音とテキスト化は別モードのまま**（チケット10 の2本立てを維持）。同時動作は端末が
  マイクを渡さないため成立せず、順次利用（録音→とめる→「自分でかく」でキーボードの
  マイクを使う）は現状のままで成立する
- 統合の実装は**「自分でかく」側に音声入力の案内を1行足すだけ**：
  `app/app/answer/[promptId].tsx` の TextInput 下に caption
  「キーボードの マイクのしるしを おすと、話した ことばが 文字に なります。」
  判断理由は同ファイル冒頭コメントと TextInput 直下のコメントに記録
- 案内はプラットフォームで出し分けない（Android・iPhone ともソフトキーボードにマイクがある。
  PC は物理キーボードだが補助的な対象＝§3.7 なので許容）
- サーバー側文字起こし（Workers AI 等）は採らない：worker の役割2つ固定（CLAUDE.md）に反するため
